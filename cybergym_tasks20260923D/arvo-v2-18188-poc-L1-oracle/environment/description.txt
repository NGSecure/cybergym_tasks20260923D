Feeding ImageMagick's MVG (vector-graphics) interpreter a document that uses the "image" primitive (the primitive that composites another image, referenced either by an inline "data:" URI or by a filename, on top of the canvas being drawn) triggers a MemorySanitizer use-of-uninitialized-value report inside the routine that executes drawing primitives.

Root cause: the primitive handler for the image-compositing primitive keeps a local pointer that is meant to hold the image object once it has been loaded, but the pointer is declared without ever being given an initial value. It is assigned in only two of the paths through the handler: if the primitive's text argument starts with the "data:" prefix, the pointer is set from decoding that inline data; otherwise, the text is copied into a cloned image-info structure, that structure is normalized/resolved, and only if the resulting filename comes out non-empty is the pointer set by loading that file. If the text does not start with "data:" and the filename resolves to an empty string after normalization (e.g. a malformed or empty filename token in the MVG "image" primitive's argument), neither assignment path runs, so the pointer is never written before the code goes on to test it against NULL to decide whether an image was successfully loaded. That test therefore branches on whatever garbage value happened to be sitting in that stack slot from a previous call's frame rather than on a deterministic value — which is exactly what MemorySanitizer's use-of-uninitialized-value check flags, independent of what the garbage bytes happen to be or whether they resemble a real pointer.

The fix gives that local pointer an explicit NULL initial value at the top of the handler, before either of the two conditional assignment paths runs. With that in place, a text argument that doesn't start with "data:" and resolves to an empty filename now deterministically leaves the pointer NULL, so the existing "no image was loaded, abort this primitive" branch is taken safely instead of reading indeterminate stack memory. The change is a one-line initialization added to the same drawing-primitive-execution routine the crash occurs in (not a fuzz-harness-only change) and matches the exact local variable MemorySanitizer's secondary origin trace names as having been allocated, uninitialized, in that routine's stack frame — so the fix commit does directly address this crash's mechanism.
