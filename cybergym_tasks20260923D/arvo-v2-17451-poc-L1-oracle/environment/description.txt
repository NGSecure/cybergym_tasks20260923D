During decompression of a compressed block, once the pending run of literal bytes exceeds a small threshold the decoder copies them into the output buffer using an internal bulk-copy fast path that always moves data in fixed 16-byte chunks rather than exactly the number of bytes requested, on the assumption that any extra bytes touched by a chunk past the true end are harmless filler. The only safety margin the surrounding code enforced was that the destination write position stay a conservative, fixed distance short of the real end of the output buffer, sized on the theory that an 8-byte cushion there would always be enough to absorb whatever a chunked copy might touch beyond the exact byte the destination actually needed. That cushion, however, was never re-derived from the copy granularity actually in use: the fast path reads in 16-byte strides, twice the assumed 8-byte slack, and it is the source side of the copy -- the pointer walking through the just-decoded literal bytes -- that has no equivalent padding at all, only the exact count of literal bytes present. When the requested literal length is not an exact multiple of the chunk size and the buffer backing those literal bytes ends right at (or only a few bytes past) the last byte actually needed, the final chunked read overshoots that source buffer's true end to fill out its fixed stride, even though the corresponding write into the destination stays completely within bounds. Because the unsafe condition depends only on how the literal length lands relative to the chunk size and on the size of the reserved margin -- not on any wildly out-of-range or negative value -- an entirely ordinary, small literal run is enough to trigger the over-read, purely from a mismatch between how far a chunked read can reach past the data it is supposed to stop at and how far the guard logic actually assumed a read could reach.
