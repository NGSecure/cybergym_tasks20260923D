This is a heap-use-after-free write, caught by AddressSanitizer, in usrsctp's outgoing-packet assembly path when a negotiated SCTP AUTH extension chunk is bundled into a packet being transmitted. The routine that builds the outgoing chunk chain runs an outer loop that iterates once per destination network address of the association (relevant whenever the peer is multihomed, or whenever more than one bundling pass is needed within a single send invocation), and it keeps a pointer to the currently pending AUTH-chunk buffer together with that buffer's byte offset. That pointer and offset are initialized only once, before the outer loop begins, rather than being reset at the top of every iteration. On an earlier pass through the loop, an AUTH-chunk buffer is allocated, populated, bundled into the packet that gets sent out, and then legitimately freed once that packet has actually gone out on the wire -- a normal release that happens once per completed send pass. On a later pass of the same outer loop within the same call, the pointer to that now-freed buffer is still sitting there, non-null, because nothing cleared it between iterations; the code treats it as if it still referenced a live, pending AUTH chunk and proceeds into the step that computes the chunk's keyed hash and bulk-writes a fixed-size digest value into the buffer at a fixed offset near its start. That write lands inside heap memory that has already been returned to the allocator, corrupting freed state (and whatever the block may have been recycled for by then). The defect is a straightforward missing-reinitialization / stale-pointer bug in per-iteration state, not a bounds check being bypassed or a signed/unsigned size mismatch: the loop-scoped auth-chunk pointer and its offset simply outlive the single iteration for which they were valid, carrying a dangling reference from one iteration into the next. Nothing malformed or protocol-violating is required to reach it -- an ordinary SCTP peer that has negotiated the AUTH extension and whose association ends up bundling and transmitting an AUTH-protected chunk across more than one pass of the destination-network output loop in a single call (for example because it is multihomed, or simply has enough queued data or control chunks to need more than one bundling pass) will cause the next pass to reuse the already-freed AUTH-chunk buffer from the previous one.
