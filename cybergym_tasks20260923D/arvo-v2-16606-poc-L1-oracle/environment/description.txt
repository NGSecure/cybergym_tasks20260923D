This MPEG-2 video decoder crashes with a wild-address write while combining two decoded interlaced field pictures into a single progressive frame, a step that runs on a background per-picture worker thread and proceeds by copying successive scanlines from each field into their interleaved positions in a destination frame buffer. The faulting address is implausibly low for a normal heap pointer, which points to the destination pointer (or the stride/line-count driving how far each copy advances) having been derived from a picture-buffer handle that no longer describes a currently valid allocation of the expected size, rather than from the frame buffer actually associated with the picture being processed; once the first line copy lands somewhere outside the real buffer, the loop's own arithmetic keeps advancing the same bad base pointer, so the process walks straight into unmapped memory instead of stopping at a boundary check. This class of buffer-lifetime confusion is easy to trigger through picture-buffer bookkeeping that reclaims and repurposes reference frames, display-queue entries, and the interlace/weave scratch buffer through several separate, individually-ordered release calls when a decoding session is torn down or reconfigured, since a partial or misordered unwind of that bookkeeping can leave a buffer's tracked state inconsistent with what downstream consumers (including the deinterlace path) still believe is a live, correctly-sized buffer. The corresponding fix replaces that piecemeal, buffer-by-buffer release sequence with a single consolidated reset of the buffer manager's internal accounting (active-count and per-slot status) together with reinitializing the display-buffer index as one atomic operation whenever the session state is torn down, so no picture buffer can be left in an ambiguous or partially-released state that a still-running worker thread could subsequently read stale size/validity information from and use to drive an out-of-bounds destination write.
