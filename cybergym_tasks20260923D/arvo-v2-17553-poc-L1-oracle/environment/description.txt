This is a multithreaded HEVC slice-decoding vulnerability triggered when a crafted bitstream omits a picture's legitimate opening (non-dependent) slice and instead presents, as the very first slice the decoder actually encounters for that picture, one whose own bitstream flag marks it as a dependent continuation slice. The decoder's internal flag tracking whether a picture is currently open is still in its not-open state at that point, but the slice-header parser does not check this before honoring the dependent-slice flag: it silently treats the missing opening slice as if it had already arrived, advances its own multi-slot slice-header bookkeeping forward by one slot, and then, because the dependent flag is set, blindly copies the previous slot's slice-header contents into the new slot as the header to depend on. That previous slot, however, holds leftover contents from an unrelated, already-finished decode of a different, differently-sized picture, not any header belonging to the picture nominally being opened now. Parsing then proceeds to fully initialize per-picture multithreaded decoding state -- including spawning worker threads and handing them a pointer into an output-buffer descriptor that physically lives inside the calling frame's stack -- using a hybrid of correctly-current parameter-set values mixed with stale, wrong-picture per-slice position and progress bookkeeping. Because that stale bookkeeping desynchronizes how many decode and output-formatting jobs the picture is expected to produce from how many actually get queued for its true, current geometry, the calling thread ends up concluding that all picture processing for this call has finished sooner than it really has, and returns -- tearing down its stack frame, including the output-buffer descriptor embedded inside it -- while a background worker thread it spawned is still dequeuing and executing a leftover formatting job that reads a pointer field out of that now-destroyed, stack-resident descriptor, yielding a read of memory that has already gone out of scope on another thread's call frame. The essential defect is a missing precondition check: a slice's dependent-slice flag is honored, and its supposed predecessor's header state is trusted and copied forward, without ever confirming that a real, non-dependent slice had already legitimately opened the current picture, so "the previous slice's header" silently resolves to whatever an entirely unrelated earlier picture happened to leave behind rather than to anything belonging to the picture actually being decoded.
