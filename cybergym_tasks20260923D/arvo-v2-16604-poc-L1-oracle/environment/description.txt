The crash happens inside the routine that converts a decoded planar YUV 4:2:0 picture into a semi-planar output layout for display, specifically while it is interleaving the two chroma planes into a single destination buffer. After copying the luma rows, the routine walks the chroma data row by row, writing one interleaved byte pair per column of the down-sampled chroma width, and then repositions the destination pointer for the next row by subtracting the picture's original (un-rounded) horizontal dimension from the configured output row stride. When that horizontal dimension is odd, the per-row byte count actually emitted by the inner loop is computed from a rounded-up chroma width and ends up one byte larger than the value subtracted back out when advancing to the next row, so the two quantities disagree by exactly one byte. Nothing corrects for that mismatch, so the destination write pointer drifts one byte further ahead than intended on every chroma row processed, and since the loop iterates across roughly half the picture height, the drift compounds row after row rather than resetting. By the final row, the accumulated forward creep carries the write pointer past the true end of the destination chroma buffer, so a write that is otherwise perfectly in-bounds for every earlier row lands one byte beyond the heap allocation sized for a non-drifting, correctly strided layout. The triggering condition is simply a picture whose width is not aligned to an even boundary, which is silently tolerated by the arithmetic that counts emitted bytes but not by the arithmetic that advances the pointer between rows, so any fix needs to make both computations agree on the same rounded width rather than letting the raw, possibly-odd value leak into only one of them.
