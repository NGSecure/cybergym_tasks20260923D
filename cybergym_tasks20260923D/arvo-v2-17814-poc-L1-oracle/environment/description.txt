This is a heap-buffer-overflow read in an FFmpeg audio decoder for a compressed sample format that leans on a small tree-like lookup table to unpack its bitstream. During stream setup, the decoder pulls a 16-bit count out of the codec's extradata header that is supposed to say how many entries populate this lookup table, and it uses that same attacker-controlled count both to sanity-check that enough extradata bytes were supplied and to size a heap allocation meant to hold that many left/right index-pair entries. The setup path checks that the supplied extradata is at least as long as the count implies, but never rejects the degenerate case where the count itself is zero, so a zero-entry table is accepted and an allocation sized for zero entries goes ahead anyway, effectively occupying no usable space. Decoding then always begins by treating index zero as the current position inside this table and walks the input a bit at a time, using each bit to pick one of two child indices out of the current entry and moving to that new position, then inspecting a field of the entry at the new position to decide whether it represents an emittable sample value or another internal node to keep following. Because the table backing this walk was allocated for zero entries, the very first access to index zero already lands past the end of the (empty) allocation, and the read of that entry's field is what trips the out-of-bounds detector, landing in unrelated heap memory rather than any real table data. The upstream correction addresses this by explicitly refusing to accept a zero-entry count during setup, closing the gap left by a length check that only ever compared the count against the extradata size and never guarded against the count being degenerately small.
