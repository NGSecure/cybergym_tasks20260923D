The crash surfaces inside a per-row image-processing generator step that converts a scanline of a legacy HDR-style, four-byte-per-pixel encoding into floating-point RGB samples, feeding a pipeline stage that is handed a row width by the surrounding region-generation machinery and a pointer into an upstream input region's own backing buffer. The conversion routine decodes the row's first pixel unconditionally, then walks the remaining width-minus-one pixels in a loop, and as a shortcut to avoid redundant decode work it compares each pixel's four encoded bytes directly against its immediate predecessor in the input stream, reusing the previously decoded colour on a match rather than redecoding. This predecessor comparison necessarily reads one pixel-unit before the current one, which is safe only as long as the row width the routine was told to process is consistent with how much real pixel data the upstream input region actually backs at that position. When the width value handed down by the region-generation machinery does not line up with the true extent of the input region's underlying buffer -- for instance because the two are derived from slightly different notions of the current valid rectangle upstream -- the loop can keep comparing pixels for longer than the input buffer actually supports, and the predecessor read walks past the buffer's real backing memory into completely unrelated, unmapped address space rather than landing just one element past a legitimate allocation. That is why the sanitizer reports a wild, invalid address rather than a narrow heap-adjacent overrun: the fault is a genuine width/buffer-extent mismatch between the row-generation and pixel-decoding stages of this HDR pixel format's conversion path, not a bounds slip local to the decode loop itself, and it requires at least two pixels of processed row width to reach the predecessor-comparison code path at all.
