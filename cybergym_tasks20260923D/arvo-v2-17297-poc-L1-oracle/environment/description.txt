This crash is reached while the Thread stack answers a Commissioner-side "get" style request over CoAP: a handler for that request pulls a declared value-length out of an attacker-supplied header field (a field whose stated width tops out at 255) and stores that length in a variable, then later hands the length along to a routine that builds the reply message. That reply-building routine trusts the passed-in length as the exact number of already-populated, valid bytes sitting in a small fixed-capacity array on the caller's stack, and walks a loop that indexes into that array once for every unit of the declared length, using each indexed byte as a lookup key while scanning a list of Network Data entries to decide what to append to the response. Because the length value is never checked against the array's real capacity before either side of this trusts it, a request that declares a length exactly one unit larger than the array can hold slips through unchanged, and on the final iteration of the reply-building loop the code reads one byte past the end of that array's memory to use as a lookup key, producing a single out-of-bounds stack read. The proof of concept reaches this path by feeding a crafted frame straight into the low-level received-frame handling pipeline (as if a peer radio had just received it over the air) rather than by driving an outbound send, so the overflow fires purely on the consuming/response side, well after whatever length-bounded copy first populated the array — the read is a narrow, one-element overrun caused by an off-by-one trust in an attacker-chosen count, not a large-scale overwrite.
