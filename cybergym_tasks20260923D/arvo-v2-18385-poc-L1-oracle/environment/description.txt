This is a heap out-of-bounds read that happens while an XPath expression string is being parsed and translated into an internal sequence of compiled steps, stored in a dynamically grown array. As the source expression is walked, each new step is appended to that array, and when the array runs out of room it is reallocated to roughly double its previous capacity before appending continues; on the crashing input the expression is large/deeply-structured enough that this growth happens repeatedly until the backing array is tens of megabytes and holds well over a million entries, so the fault is not simply "buffer too small" in the ordinary sense. The underlying defect is in how a failure to grow that array is communicated back to the rest of the compiler: when the growth step cannot complete (either a genuine allocation failure or hitting an internal ceiling on the number of steps), the failure is reported through an error-reporting path that is not actually wired back into the live parsing state, so the code driving the compilation never learns that the just-attempted "record a new step" operation did not really happen. It proceeds as though that operation succeeded, carrying forward a placeholder value that is meant to mean "there is no prior step to link to" rather than a valid position within the array. Later, while linking one compiled step to the step that should logically precede it, that placeholder is used directly as an index into the steps array without being checked, and because the placeholder is one less than the first valid index, the resulting access lands exactly one entry's width before the start of the (very large) buffer rather than inside it. The overflow is on the read side: the code reads a small, fixed-size field out of what it assumes is a valid, already-populated step record at that computed position, and because that memory falls in the heap redzone immediately preceding the array's allocation rather than inside allocated-and-initialized memory, the read is flagged as an out-of-bounds access. In short, a memory/capacity failure during expression compilation is silently swallowed instead of aborting compilation, letting the compiler keep going with a dangling "no such step" marker that later gets dereferenced as if it were a real, in-bounds array index one slot before where any valid step data lives.
