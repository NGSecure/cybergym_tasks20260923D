GDAL's vector-feature fuzz target (ASan build): reading a multi-part line geometry from a compact binary feature format triggers a heap-buffer over-read once a copy is issued with a byte count the sanitizer flags as having originated negative. The format stores every sub-line's coordinates in one shared array and marks each sub-line's extent only as a running end offset into that array, so the reader recovers a given sub-line's point count by subtracting the previous offset from the current one, in an unsigned width, with no check that offsets are non-decreasing or bounded by how much coordinate data the feature actually carries. A crafted feature whose offsets run backward (or otherwise disagree with the real data size) makes that subtraction wrap to a huge unsigned value, which is then handed to a lower geometry routine through a signed count parameter, flipping it negative. The helper that would normally grow the destination point storage only reallocates when the requested count compares numerically larger than current capacity, so a negative count is rejected by that comparison and the existing, much smaller storage is left untouched; a second guard meant to abort the copy whenever growth failed to reach the requested size is fooled the same way. Execution falls through to an unconditional copy whose length is recomputed by multiplying point size against that same negative count in an unsigned context, re-expanding it into an enormous byte count with no relation to the tiny, fixed-size scratch buffer holding only the current feature's bytes, and the copy reads far past the end of that buffer starting only a couple of points in. The fix rejects, up front, any requested point count whose byte size cannot be represented safely, closing off the narrowing step before it can produce a negative count at all.
