This crash surfaces while emulating a big-endian AArch64 double-to-single floating-point conversion instruction, deep inside the soft-float helper chain that services that opcode. Before the helper does any real work on the operand, it first branches on a per-emulation floating-point control flag that decides whether the flush-to-zero handling of denormal inputs should be applied; that flag lives in a small floating-point-status structure that is supposed to be fully populated as part of setting up CPU/FPU state for the emulated core. On this code path the structure is only partially initialized ahead of the conversion helper being reached, so the read of that specific control flag pulls in bytes of memory that were allocated but never assigned a value, rather than a value actually derived from the instruction's real operand or from an explicit configuration call. Because the very first conditional in the denormal-squashing routine depends directly on this unset flag, the taint is detected immediately, before the routine ever gets to inspect the mantissa or exponent of the value being converted — the uninitialized read is a control-flow gate, not a bug in the arithmetic itself. The condition is architecture- and endianness-specific: it is reached only through the big-endian AArch64 double-precision narrowing path, so any state-initialization path that only covers the more commonly exercised little-endian or single-precision variants leaves this particular flag unset when execution instead runs through the aarch64eb double-to-float conversion helper, and MemorySanitizer flags the read as soon as that helper is invoked with a floating-point status block that was never fully cleared or assigned along that path.
