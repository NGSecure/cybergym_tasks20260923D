This MATLAB MAT-file (version 5) parser reports a use-of-uninitialized-value fault while it is walking into a struct field or cell-array element nested inside a larger variable, i.e. the crash fires only after the reader has already recursed at least two levels deep into a container's fields or elements. Every fixed-size binary word the reader consumes while decoding a variable's header and payload -- the array-flags word, the dimension words, the name-length and name bytes, the data type/size tag word and, whenever the size does not fit inside that tag, a following continuation word, plus the analogous tags used for sparse index counts and for the real/imaginary halves of complex data -- goes through one shared low-level byte-read helper. That helper had a single way of reporting a short read: normally, failing to transfer the full requested byte count was treated as an error, but as a special case for the very first read attempted at the true boundary between one top-level variable and the next, hitting end-of-file with zero bytes transferred was silently remapped to success rather than failure, on the reasoning that running out of file exactly where a new variable would begin is the ordinary, expected way a MAT stream ends. That leniency was never actually scoped to just that one legitimate boundary, though; the same zero-bytes-read-equals-success behavior applied uniformly to every other call site reusing the same helper, including reads that occur strictly in the middle of parsing an already-in-progress variable's structure, such as the continuation word of a size tag or the tag word immediately preceding a nested field's or element's own payload. A crafted stream can be truncated exactly at one of these interior points instead of at a genuine between-variables boundary, which makes an interior read come back with zero bytes transferred; the helper reports that as a clean, successful read, so the small fixed-size on-stack buffer meant to receive those bytes is left holding whatever unrelated data happened to already sit on the stack from earlier calls, and the surrounding code goes on to byte-swap and interpret that never-written buffer as if it held a value genuinely read from the file -- exactly the read of uninitialized stack memory that the sanitizer flags. The corrective change narrows the lenient EOF-is-success behavior to only the handful of call sites that read the very first word marking the start of a fresh top-level variable, and makes every other use of the same helper strict, so any short read there -- end-of-file included -- is now treated as an outright parse error instead of silently letting stale stack contents pass for real file data.
