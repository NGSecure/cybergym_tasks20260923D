While parsing a crafted vector-geometry file, the reader for one of GDAL's binary feature formats decodes a polygon-like geometry whose rings are stored as one shared flat array of coordinate values, with each ring's boundary marked by an offset value read straight out of the input rather than derived from the array's own true length. The reader computes how many points belong to a given ring by subtracting one such attacker-controlled offset from the previous one, and forwards that count, unvalidated, into the lower-level routine that copies the ring's coordinates into a freshly sized internal point buffer. Because nothing checks that the resulting ring extent, or its cumulative offset within the shared coordinate array, actually stays inside the bounds of the coordinate data the file supplied for the feature, a small number of crafted, inconsistent boundary values is enough to make the derived ring size come out far larger than what backs it, sometimes by many orders of magnitude. That implausibly large count is then multiplied by the size of one coordinate pair to determine how many bytes to copy, and the resulting byte count is so large it is caught by the runtime's own sanity check on copy sizes before any actual out-of-bounds memory access can occur, aborting the process outright. The underlying condition is a missing bounds check between an externally supplied ring-boundary marker and the true size of the coordinate storage it is meant to index into, not an arithmetic overflow in the point count itself, and it can be reached from a polygon with as little as two rings whose boundary entries are not monotonically consistent with the actual coordinate payload length.
