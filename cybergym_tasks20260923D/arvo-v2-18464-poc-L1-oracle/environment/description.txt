This crash shares the same underlying step-back-past-the-end defect as the bareword-scanning case, but it is triggered from the tokenizer's top-level dispatch state rather than from inside an in-progress string token. At the start of deciding what kind of lexeme comes next, the top-level scanner performs a single-character lookahead: it reads the next byte to inspect it, then immediately steps the cursor back by one so that byte is still available to be consumed by whichever specific branch (equals sign, comment, quoted string, multi-line string, variable reference, bareword) turns out to match. That step-back operation is the same unconditional primitive used elsewhere and likewise assumes a byte immediately behind the cursor is always safe to inspect. The fault appears when this top-level lookahead is attempted exactly at the point where the input the parser was told about has just been exhausted: the read that detects end-of-input takes a path that never dereferences past the boundary, but the immediately following, unconditional step-back does, landing one position beyond the last byte of the fixed-size buffer the fuzz harness supplied. Unlike the bareword-token variant, this happens before any specific token type has even been chosen, making it reachable from the very first byte-boundary condition the top-level dispatcher hits, independent of what kind of value follows.
