The crash surfaces in the color-space conversion stage that runs while an image is being encoded for output, specifically the step that decodes a packed, four-samples-per-pixel representation (an exponent-shared triplet format borrowed from a well-known HDR image encoding) back into ordinary floating-point color values. That packed representation is only valid when the image object's declared band count and per-band storage type match the fixed four-byte-per-pixel layout the decoder assumes; the routine that parses a native-format image header accepts and honors a "packed/coded" flag in the file without cross-checking that the accompanying band-count and per-band-type fields actually describe that same four-byte layout, so a crafted header can set the flag while giving the image a narrower true per-pixel storage size than the packed format requires. Later, when the conversion pipeline processes a scanline of such an inconsistent image, it computes how many packed units to consume purely from the image's declared width rather than from the smaller buffer that was actually allocated for the real (mismatched) band/format combination, and each unit read also uses its trailing exponent byte to scale the resulting color magnitude. As the per-pixel loop advances across the row it steps forward using the packed format's stride even though the underlying buffer was sized for the narrower, mismatched layout, so successive one-byte reads land at increasing offsets beyond the buffer's true end; once far enough along the row this walks off the end of the memory region entirely and touches an address the allocator never tracked, which is reported as an out-of-bounds read against a wild pointer rather than a bounded heap-adjacent overrun.
