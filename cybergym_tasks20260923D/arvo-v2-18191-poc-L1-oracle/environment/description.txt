ImageMagick's XPM (X PixMap) colormap parser (MSan build): decoding a crafted XPM image's colormap section trips a use-of-uninitialized-value warning while classifying one colormap row's color-name token. Root cause: the decoder keeps one fixed-size stack buffer, reused across colormap-row iterations, to hold the current row's color-name token. Before extracting the token it seeds the buffer with a short default word via a bounded string copy, but never clears the rest of the buffer's storage. The buffer is then overwritten by a second bounded copy that pulls raw characters from the XPM syntax up to a caller-supplied byte-length cap; that copy helper counts down its remaining budget on every step — including the final step where it discovers the source's real stop point — and only appends a terminating NUL if any budget units remain after that last countdown; because that last countdown consumes one unit even when the copy loop does nothing else on it, the helper drops the terminator specifically when the source's real content is just one byte short of the cap it was handed, not when the content fills the cap exactly. (When the content genuinely runs the whole cap with no stop point in range, the countdown instead wraps past zero into a huge nonzero value, so the "budget still left" check is fooled into firing anyway and a NUL does get written — that fuller-looking case is actually the safe one; it is the near-miss, one-byte-short case that silently drops the terminator.) Immediately after, the same buffer is handed to a routine that walks it byte-by-byte hunting for that NUL to find where the token ends. With no terminator written, the scan runs past the copied prefix into the trailing portion of the buffer that neither the seed copy nor the token copy ever touched, reading uninitialized stack bytes and tripping the sanitizer. Whether that trailing region happens to hold leftover (already-initialized) bytes from a prior loop iteration or genuinely virgin stack memory depends on the exact token lengths seen across iterations, and the reported crash lands on the buffer's very first fill, where the tail past the seed word has never been written by anything at all.
