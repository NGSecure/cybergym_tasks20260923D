This is a heap-buffer-overflow read inside a SIMD-accelerated pixel-sample loading routine used by Skia's rasterizer when copying two interleaved 16-bit color channels (for example red and green) out of a source pixel buffer that was heap-allocated to hold exactly the bytes needed for the image's raw pixel data. The routine's fast path pulls a full vector's worth of pixels at once, but when fewer pixels than that remain at the tail of the buffer it takes a separate narrower path that further branches on exactly how many trailing channel-pairs are still valid, assembling the result a few bytes at a time for very small counts. The vulnerable branch is the one reached when only a single interleaved channel-pair, i.e. four bytes total, is left to read: instead of issuing a load sized to those four bytes, it uses a single wide-load instruction whose intrinsic unconditionally fetches eight bytes regardless of how many are actually wanted, so when that last valid pixel sits flush against the end of the allocation, the extra four bytes are read from adjacent unallocated heap memory. Because that adjacent region is poisoned heap redzone, the sanitizer flags the read; on a non-instrumented build the surplus bytes would just be garbage silently folded into subsequent color computation without any observable fault. The root cause is a mismatch between the fixed, compile-time width of the load instruction chosen for that particular small trailing count and the true, count-dependent number of valid bytes remaining — the size/tail-count bookkeeping that selects which branch to take is itself correct, it is only the width of the load chosen inside the smallest-count branch that overshoots. The fix narrows that specific branch to a load that reads exactly the four valid bytes it needs instead of the wider eight-byte instruction, leaving every other trailing-count case unchanged.
