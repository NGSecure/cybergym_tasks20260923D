This is a heap out-of-bounds access in an Android HEVC (H.265) software video decoder, hit during ordinary per-block bitstream parsing when the entropy-decoding context for the current slice fails to initialize partway through decoding. In that failure branch the decoder does not abort the current coding-tree block outright; instead it takes a recovery path that writes a handful of small default in-loop-filter (sample adaptive offset) parameter fields directly into a per-block record inside a flat, frame-wide array, locating that record by multiplying the block's row position by the frame's block-grid width (in coding-tree-block units) and adding its column position. The array itself, however, was sized much earlier, at decoder-initialization time, by a separate calculation that derives the number of block columns and rows from plain integer division of the frame's pixel width and height by the nominal block size, discarding any remainder — unlike the frame's authoritative block-grid dimensions used everywhere else in the decoder, which round that division up to account for a final, narrower row or column of blocks. Whenever a frame's pixel dimensions are not an exact multiple of the block size, which is common and fully standards-compliant, every block in that trailing partial row or column resolves to a record slot beyond the end of the undersized array. Because the fields being defaulted are narrow, sub-byte bit-packed values, writing even one of them requires the compiler to first load the full storage word that holds it so the surrounding bits can be preserved, and it is that preliminary load, landing outside the array, that the crash actually reports, even though the code's intent at that point is a write.
