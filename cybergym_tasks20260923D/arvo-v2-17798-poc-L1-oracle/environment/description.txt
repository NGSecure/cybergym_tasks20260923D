A crafted MVG (ImageMagick's vector-graphics text format) input, fed through the ping-only decode path, triggers a use-of-uninitialized-value read while the MVG interpreter is converting an elliptical-arc "path" segment into a series of cubic-bezier points.

Mechanism: while walking the arc, the interpreter emits one cubic-bezier sub-segment per loop iteration by calling a shared bezier-tracing helper and combining its per-call success/failure flags with a bitwise AND into a running status variable. That helper can bail out early — for example when the coordinate span it needs to allocate scratch buffers for is unreasonable, or its own follow-up growth of the shared primitive-coordinate array fails — and on that early-exit path it returns without ever writing the point-count field of the array slot it was supposed to fill in. The arc loop does not check the running status before continuing; after each call it unconditionally reads that same slot's point-count field to advance its cursor and, once the loop ends, to compute the arc's overall point total. Because the primitive-coordinate array had just been grown by a realloc-style reallocation a few calls earlier in the MVG renderer (which does not zero freshly-grown memory), the slot the failing bezier call was responsible for was never actually written before it gets read back — MemorySanitizer flags exactly that read (and the loop bound it feeds) as uninitialized.

In short: value flow is heap-grow (realloc, no zeroing) → a per-segment helper that can exit before populating one field of its assigned array slot → its caller's loop unconditionally trusting that field to already be populated. The bug is a missing failure check on the per-segment helper's return value inside the outer arc-tracing loop, not a wrong bounds check or an off-by-one.

Fix-commit assessment: `patch.diff` for the recorded fix commit only touches a completely different part of the same source file — it hardens a small text-tokenizer used while parsing "push"/"pop" graphic-context blocks and macro definitions elsewhere in the MVG interpreter, making that tokenizer's call sites check its return value and bail out of their loops instead of ignoring a failed/empty read. That code path handles graphic-context nesting keywords, not arc/bezier geometry, and none of its hunks touch the arc-tracing function, the bezier-tracing helper, or the primitive-array growth call implicated above.

Directly diffing the vulnerable and fixed source trees (not just the recorded commit's diff) shows the arc-tracing function did change between the two: a redundant absolute-value call was dropped, a near-zero-denominator guard was added before a reciprocal division, and — the change that actually matches this crash — the per-segment bezier-helper's running status is now checked inside the loop, breaking out (and returning failure to the caller) as soon as a single segment call fails, instead of continuing to read that segment's uninitialized point-count field. That guard is exactly what this crash needs and is present in the fixed tree, but it is not part of the hunks in `patch.diff` — i.e. it belongs to a different commit than the one recorded as `fix_commit`. Consistent with that, the crash function itself is not among the recorded fix's touched-function list, only two unrelated parsing functions are. Given the very large number of commits associated with this id (a multi-day bisection range rather than a single pinpointed commit), this looks like a case where `fix_commit` may be wrong — a bisection-range artifact rather than the actual patch for this crash — and the real fix should be attributed to a different, unidentified commit in that range whose diff touches the arc/bezier tracing code directly.
