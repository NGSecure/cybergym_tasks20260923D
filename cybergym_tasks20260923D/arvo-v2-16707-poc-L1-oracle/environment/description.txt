This crash surfaces while an image object that was just opened from an untrusted source is being prepared for output as a JPEG: before any pixel data is written, the save path has to decide how to get the image into a shape the encoder can accept, and it makes that decision by reading a small integer tag stored on the image that records which of a short, fixed list of internal coding/packing schemes the pixel data is currently in. That tag is used directly as an index into a small, fixed-size lookup table of per-encoder capability flags, on the assumption that the tag can only ever hold one of the handful of legitimate values defined for that enumeration. The header-parsing step that fills in this tag (along with a closely related tag describing colour/interpretation) does not clamp or otherwise validate the raw value it read off the wire into that legal range before storing it on the image object; a corrupt or truncated source file can therefore leave the tag holding a value larger than the highest legitimate coding scheme. When the save logic later uses that oversized value as the table index, it reads memory past the end of the small table instead of a valid capability flag, and dereferencing/using that out-of-bounds result is what produces the segmentation fault seen here. The read is a genuinely out-of-bounds access rather than a null-pointer or use-after-free issue, it triggers deterministically for the same malformed input, and it is specific to output/conversion-readiness logic that trusts an unchecked enum-like field carried on the image object rather than to any parsing of the JPEG data itself; the underlying defect is the missing range clamp at image-header ingestion time, not anything in the encoder that ends up indexing off the bad value.
