This crash lives in the file/libmagic library's parser for the Compound Document Format container (the structured-storage format used by legacy Microsoft Office documents), on the code path exercised when type detection falls through to sniffing a document's internal property sets, such as its summary-information stream. While walking one of these property sets, the parser reaches a case for reconstructing a variable-length ("vector") typed property value and reads, directly from the untrusted input bytes, a count of how many elements that vector holds. This count is validated only against the degenerate case of being zero; no upper bound is enforced before the value is used for two separate purposes further down: sizing how large an internal decode buffer needs to be grown to, and, independently, bounding a loop that writes one decoded element per iteration into that same buffer. Because the input file is fully attacker-controlled, this element count can be set to an implausibly large value that has no real backing data in the document, so that the buffer-growth sizing and the write-loop's iteration bound end up computed inconsistently with each other from the same oversized figure — the loop keeps writing a few bytes beyond where the just-grown allocation actually ends. AddressSanitizer reports this as a small (4-byte) out-of-bounds heap write, landing just past the tail of the most recently grown decode buffer, when a crafted document supplies a vector-typed property whose declared element count is unchecked and far larger than the data actually available to fill it.
