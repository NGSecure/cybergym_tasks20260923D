This bug lives in a small helper that builds every combination path across a list of candidate selector groups, used while resolving how a nested rule's parent-selector references expand against its enclosing selectors. The helper first counts how many groups it was given and, from that count, derives a position value by subtracting one, on the assumption that the count is always at least one so the result identifies a valid last-group index; it then allocates a small per-group state buffer sized to that same count and walks through it. The code already guards against the case where one of the groups inside a non-empty list is itself empty, but it has no matching guard for the degenerate case where the whole list of groups is empty to begin with. When that happens, the subtraction is performed on an unsigned count of zero, so instead of yielding a small "no valid index" style value it wraps around to an enormous position number, while the just-allocated state buffer ends up zero-sized. The subsequent loop then indexes into that buffer using the wrapped-around, far-out-of-range position, landing on heap memory that this buffer never touched or initialized rather than on a bounds violation that would abort immediately, which is what surfaces as a read of uninitialized memory. The path that reaches this state arises when the selector-expansion machinery hands the helper a completely empty outer list of parent-candidate groups, as opposed to a list containing one or more empty entries, something that can happen for certain constructions involving deeply nested rules and parent-selector references where no enclosing selector groups end up being contributed at all.
