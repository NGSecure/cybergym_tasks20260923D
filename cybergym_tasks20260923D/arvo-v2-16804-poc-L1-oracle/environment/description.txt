This is a heap out-of-bounds read in an Android HEVC (H.265) software video decoder, triggered while the decoder performs its bookkeeping for motion-vector prediction once it has finished parsing a coding-tree block near the far edge of a frame. To let later blocks reference this block's already-decoded motion information, the decoder keeps a small per-picture table that stores, for every column of coding-tree blocks across the frame's width, an index pointing into a much larger array of per-block motion records; this small table is allocated with just enough room for the number of columns implied by dividing the frame's pixel width by the decoder's nominal coding-tree-block size, plus one extra guard slot. When the decoder later looks up the correct slot for the rightmost column, it computes the position by multiplying the column number by that same full nominal block size, implicitly assuming every column spans a complete, full-width block. Real-world frame widths are frequently not an exact multiple of the coding-tree-block size, so the final column is legitimately narrower than the nominal size; in that ordinary, standards-compliant case, the multiplication still uses the full size, producing an index a few elements past the true end of the small lookup table and causing the decoder to read stale heap memory just beyond it. The read pulls in an attacker-influenced index value that then feeds directly into subsequent per-block prediction logic, so the out-of-bounds value is not a transient miscalculation but is treated as trustworthy state describing where a neighboring block's data lives.
