In this HEVC slice decoder, per-slice bookkeeping (including the counts and used-by-current-picture flags describing which already-decoded pictures serve as short-term references for the picture being parsed) lives in a small, fixed pool of reusable slots that cycles across successive slices rather than being freshly allocated each time; when the current slice's reference-picture lists are later assembled, the code builds one running total for short-term references actually used by the current picture and, cumulatively across both halves (nearer and farther) of the short-term set, a second running total for references that are not used now but are still needed by future pictures, writing one entry into a fixed-capacity local array — sized only for the decoder's ordinary per-picture reference-count ceiling — for every picture folded into that second, cumulative total. Because the reusable slot is not fully reset before being handed to a new slice, a slice whose own bitstream does not end up re-establishing every field feeding that accounting (for instance, one that resolves its short-term set by looking up an already-parsed entry rather than re-parsing its own, or one whose own parse of a fresh set errors out or is otherwise cut short before every count field gets rewritten) can silently inherit a larger, unrelated reference-set size left behind by whichever earlier, differently-sized slice last occupied that same slot. That leftover count is trusted as-is rather than being re-checked against the fixed array's real capacity, so the assembly loop keeps writing further "not used yet, but needed later" entries past where a legitimately-sized slice would have stopped, and the write for one of those extra, spurious entries lands just past the end of the array on the stack, clobbering an adjacent local variable's storage. The corrective change closes this off by forcing the entire reusable slot back to an all-zero state at the exact moment it is claimed for a new slice, before any of that slice's own fields — including the ones driving this reference-set accounting — are populated, so a slice that never gets around to re-establishing a given field can no longer inherit a stale, oversized value carried over from whatever earlier slice previously used that slot.
