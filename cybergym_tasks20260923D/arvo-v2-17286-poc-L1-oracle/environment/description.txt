libhevc's HEVC frame decoder (ASan build): after a slice's syntax elements have been parsed, a separate worker thread walks the frame one coding-tree block at a time to build a per-block map of motion-vector/prediction-unit indices that later pictures use for collocated motion-vector prediction, computing for each row and column of the current block how many minimum-prediction-unit cells actually remain inside the picture's declared width and height and writing one entry per remaining cell into a buffer whose size was fixed from the frame's coding-tree-block geometry at allocation time. The decoder does not reject a bitstream that re-signals the sequence-parameter-set identifier already in use for the current picture with a different coding-tree-block size before that picture's working buffers are torn down and resized for the new geometry; when decoding continues on buffers still sized for the earlier geometry, the remaining-cell counts derived from the picture's current width and height can run larger than what the buffer actually holds, so writing the final cell for a block overruns the end of the allocation by a few bytes, producing a heap-buffer-overflow write on the background thread that performs motion-vector processing rather than on the thread doing bitstream parsing.
