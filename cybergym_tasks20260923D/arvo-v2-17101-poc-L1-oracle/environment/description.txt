This crash happens inside the regular-expression compiler's pattern-parsing pass, specifically in a small optimization that looks at a two-member bracketed character class (such as a letter written in both cases) and tries to fold it into a single, caseless literal-character match instead of a full class. To decide whether the class's two members are true case partners, the compiler needs the case-folded counterpart of the first member, and it obtains that by indexing directly into a small, fixed 256-entry case-folding table using the member's raw numeric code-point value as the array index -- before it has checked whether that code point could be a value the table was never sized to hold. A separate branch, reached only when the pattern is compiled with wide/Unicode-codepoint support and the value is large, is meant to substitute a proper Unicode-aware case mapping instead of consulting the small table at all, but in the vulnerable version that substitution merely overwrites the result of the table lookup after the lookup has already run unconditionally. So whenever a bracketed two-character class contains a code point large enough to fall outside the table's single-byte range, and the pattern is compiled in the mode that actually allows such large code points to appear, the fixed table still gets dereferenced with an out-of-range index, producing a read that lands far outside the table's backing memory and crashes the process; the eventual, correct substitute value computed for the wide-codepoint case never gets a chance to prevent the bad read, because it is computed too late, after rather than before the unsafe lookup. The fix reorders this logic so the code-point range is checked, and the wide/Unicode case short-circuited, before the fixed-size table is ever touched, guaranteeing the table index always stays inside its bounds.
