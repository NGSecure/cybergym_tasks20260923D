matio's MAT v5 numeric-element reader (MemorySanitizer build) fetches a small fixed-size marker from the input stream that packs together the element's data type and byte count before deciding how much data to expect and how to interpret it; the read call that fills this marker is invoked without checking whether it actually succeeded. Here the trigger is directory enumeration rather than a full data fetch: the library is walking the field list of a compound (struct-like) variable purely to build the archive's listing of contained entries, and that walk re-enters the same numeric-element reader to inspect one of the struct's individual sub-fields. The marker consumed in this path is the two-part long form, where the type word and the byte-count word are read as separate steps; the type word is read successfully, but the input ends before the following byte-count word can be filled. Execution proceeds regardless, and the leftover indeterminate byte-count value is passed through the module's endianness-reordering helper - so the tainted value is explicitly copied/transformed before use rather than read in place - and the reordered-but-never-written count then governs how much of that struct field's data gets pulled in next, which is what the sanitizer flags as a use of unread memory.
